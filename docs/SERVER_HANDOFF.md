## 2. 不可突破的边界

- 只读：不索取、读取或保存用户私钥，不连接实盘钱包，不新增线上签名/广播路径。
  不通过提交“空钱包交易”“无效交易”来测试排序器延迟。
- 保留 RPC 方法允许列表，所有输出 `copy_eligible=false`。
  如果新只读功能确需扩展方法，逐项说明用途、增加拒绝广播的测试，不能取消允许列表。
- 未经单独确认，不购买 RPC/云资源，不启用付费订单 API，不发 Telegram 消息，
  不安装常驻服务、不改防火墙或现有生产服务；Git 提交、推送另按用户授权执行。
- 不为通过测试而关闭新鲜度检查、身份校验、回执隔离、去重、容量限制或限流保护。
  网络/权限受限时说明问题并申请正常授权，不绕过限制。
- 保存原始样本和来源；新增样本单独存放，不改旧证据来匹配实现。
  运行日志放在已忽略的 `var/`；精选回归样本进入 `data/` 前检查凭据和来源。
- 金额用整数计算，JSON 中序列化为十进制字符串；不使用浮点币额。

执行路径与经济行为必须分开：

| 模式 | 当前能力 | 不得推断的结论 |
| --- | --- | --- |
| direct | 签名恢复钱包身份，解析部分已知方法 | 钱包发起的每笔交易都是买卖 |
| self_account | 两类已知 7702 账户的批量调用布局 | 所有账户实现和子调用均已支持 |
| bundled_account | 已知 EntryPoint / handleOps 按 UserOperation.sender 解包及日志隔离 | 一笔 bundle 有 Swap，所有用户都参与了这个 Swap |
| third_party | 部分被动入账、外部交付候选、批量分发汇总 | 收到代币就是买入，或已证明 Solver 为此钱包履约 |

领奖、转账、授权、存款、LP 操作不能直接当买卖；`claim + swap` 必须保留 swap。
不能仅按收款人数丢弃整个批次；未知路径保持 UNKNOWN / needs_review。
意图、观察到执行、有限兑换证据不同，均不代表 L1 最终性、盈利或实盘许可。

## 3. 第一阶段：复现服务器基线

### 3.1 环境核对与安装

已有仓库则直接进入，不重复克隆或覆盖。新机器首次拉取可用：

```bash
git clone git@github.com:jelly-man-2024/smart_money_copytrader.git
cd smart_money_copytrader
git status --short --branch
git rev-parse HEAD
python3 --version
uname -sm
```

SSH 需要该服务器具有仓库读取权限。原机器曾通过 HTTPS 推送，
不代表新机器已经拥有任何 GitHub 登录凭据；不要复制或输出旧凭据。

目前验证过 Linux x86_64 / Python 3.10.12。其他 Python 版本或架构先跑完整测试，
不能直接声称已兼容。保留已有虚拟环境；若明显不兼容，使用新环境而不是删除旧环境。

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.lock -e .
.venv/bin/python -m pip check
.venv/bin/python -m unittest discover -s tests -v
.venv/bin/sm-copy replay --extra-fixture data/bulk_distribution.json --db :memory:
```

基线预期：46 项单测通过，13 笔样本回放生成 27 个信号，全部不可实盘。
行为统计：TRANSFER 1、CLAIM 1、APPROVAL 12、UNKNOWN 6、SELL 1、BUY 1、
LIQUIDITY 1、EXTERNAL_DELIVERY_CANDIDATE 1、INTENT_DEPOSIT 2、BULK_DISTRIBUTION 1。
这些数字是历史版本回归参照，后续合理扩展可改变统计，但必须解释差异、保留安全负例，
不能删测试或放宽断言只为满足新实现。

特别核对：230 个收款人、32 个清单地址的分发只输出一条分发汇总，不是 32 个买单。
离线能复现买卖意图不等于已经核实原生 ETH 净成交。

### 3.2 首次联网：只跑有限时观察

默认使用项目内的公共 HTTPS RPC 和 WSS Feed，不需要用户钱包或先购买服务。
如果用户已经提供允许使用的专用 RPC，用现有安全方式设置 `ROBINHOOD_RPC_URL`；
不要要求把含 key 的 URL 粘贴到对话或日志。`.env.example` 不会自动加载。

使用独立测试数据库；下面路径如果已经存在，换一个新的运行路径，不删除旧结果。
记录本次运行的实际路径，避免跨 shell 依赖未保留的变量。

```bash
.venv/bin/sm-copy monitor --seconds 60 --db var/server-smoke.sqlite3
.venv/bin/sm-copy export --db var/server-smoke.sqlite3
```

60 秒不包含所有启动与收尾时间，另有初始 RPC、最多 15 秒队列排空等开销。
不要首次接手就用 `--seconds 0` 无限运行。冒烟测试通过后，可再做有明确结束时间的
30 分钟只读观察；24 小时运行或常驻部署先确认运行方式和资源预算。

分开保留 stdout（信号 JSONL）和 stderr（健康及统计 JSON），不要把二者混为交易信号。
检查退出状态和日志内容：当前正常退出不代表运行期间没有错误。

- 连通性：链 ID 正确，存在 `feed_connected`，消息持续到达并追上新鲜数据。
- 健康性：关注 `health`、`monitor_finished` 中的 counters、队列长度，
  以及 `queue_overflow`、`candidate_error`、`receipt_unavailable`、`drain_timeout`。
- 候选链路：有候选时核对身份、回执、分类及数据库。没有候选时只证明采集链路，
  不算候选解析失败，也不能算完整链路验收通过；用回放补充覆盖。
- 明确记下 `queue_drops`、`worker_errors`、`account_code_errors`、
  `receipt_unavailable`、`reconnections`、`frame_errors` 的数量和原因。
  初始化追历史消息与持续掉队要区分，不能仅看 `stale_transactions_skipped` 总量。

过去的 15 秒只读测试接收过 600 帧、解码 625 笔新鲜交易并命中 1 笔候选，
仅证明当时接入成功，不是服务器的最低吞吐要求、覆盖率或稳定性保证。

## 4. 先补测量，再评价速度

普通功能测试不要求美东。旧工程在 Ohio 的测试更快，可把 `us-east-2` 作为对照候选，
但不保证当前 Feed、RPC、排序器位于同一地点或仍具有同样延迟。
当前配置建议只是估算：2 vCPU / 4 GB / 50 GB SSD 起步；资源是否足够以实际运行判断。

当前程序没有完整的端到端延迟埋点。要做性能报告，应先增加只读指标并验证其开销：

- 本地首次接收、解码结束、候选入队/出队、RPC 开始/结束、回执首次可用、落库时间。
- CPU、RSS、事件循环延迟、队列长度、磁盘增长、网络字节数和重连情况。
- 分阶段的样本数、p50/p95/p99，区分冷连接、稳定连接、追历史和重连时段。

同机耗时使用单调时钟；跨机按相同 tx hash（必要时 Feed 序号）配对，记录 UTC 接收时间，
并验证两机时钟偏差。链上 header.timestamp 不能当作精确的亚毫秒发送时间。
回执首次可用时间受轮询频率、网络和服务商影响，不是纯链上执行延迟。
不得把新观察器的结果与旧工程的提交接口响应 1.53 ms 混为成交耗时。
Feed 是已排序数据，较早看到它也不能保证插到目标交易之前。

## 5. 后续开发：按验证结果推进 M2

先汇报基线结果和短计划，然后直接推进可安全完成的只读改动；不要只反复输出方案。
以下优先级是新服务器接手顺序，不改变完整方案的里程碑定义。
一次做一组可验证的小改动，不重写整个项目；每组都补测试、回放、更新交接记录。

### P0：修复基线问题与可靠采集

涉及 `cli.py`、`feed.py`、`rpc.py`、`store.py`。

- 修复实测崩溃、超时、队列积压、阻塞与错误不可见问题；保留有界资源使用。
- 持久化处理进度和待处理候选，补齐断线/重启补漏、回执重试、幂等处理。
  不能假定 Feed 序号就是 L2 区块号，需验证映射或使用独立区块游标。
- 当前队列满时候选可能已进入内存 seen，但没有成功入队；补测试确保不会永久漏掉。
- 对限流使用有界重试、退避和可观测状态；当前固定一秒重连不等于完整限流处理。
- 区分实时信号和补抓历史信号：历史补抓不得伪装成新鲜机会。
- 添加规范链区块哈希复核、重组撤销/重算，避免 SQLite 状态只能提升而不能纠正。

验收包含：重启恢复、掉线后缺口、重复输入、队列溢出、RPC 429/超时/晚到回执、
失败 UserOperation、重组及旧数据不误报实时信号。故障优先用本地 mock 注入，
不通过大量请求或频繁真实重连来压测公共端点，也不改服务器公共网络制造故障。

### P1：严格的成交确认

涉及 `decode.py`、`receipts.py`、`registry.py`，保持逐子调用和逐 UserOperation 的归属。

- V2/V3 factory 与池地址、token0/token1、部署代码/版本验证。
- V4 完整结算接收人、输入/输出资金对应及多跳；未知 hooks 保守处理。
- ETH 支出/收入、退款、Gas 分离；需要可验证的 trace 或状态差分，缺数据继续 review。
- 智能账户委托须考虑目标执行时状态；简单读取 latest 甚至块末状态也未必能证明
  块内目标操作之前的委托有效性，无法确定时标记限制。
- 保留多 swap、未知兄弟调用、部分失败、伪造事件、recipient 非目标钱包等负例。

不能仅凭外层成功、一个 Swap 日志、交易 value 或钱包一次收币确认买卖。

### P2：被动入账兜底与 Solver 订单归属

- 当前候选只看恢复出的发送者或 calldata 中的地址字节。
  收款人只存在于链上状态时会漏检，需增加有界区块/Transfer 日志兜底。
- 将同一业务的源支出、存款、目标链兑换、交付按可核对的订单证据关联。
  不假定 `orderId` 就是 API 的 `requestId`；仅 Robinhood 数据可能不够。
- 缺源链/订单权限时，继续保留交付候选，不伪造 BUY；为解析器准备公开或脱敏回归样本。
- 如需新增 `eth_getLogs` 等只读方法，按第 2 节审查允许列表、范围限制和重试策略。

遇到需要新权限的订单 API 可以报告阻塞，继续完成不依赖它的只读适配和测试。
不要自行购买 API 服务或反复索取钱包私钥。

### P3：纸面跟单，不是实盘执行器

在受支持路径的成交证据、采集可靠性过关后，再接实时可得报价和模拟账本。
计入价格偏离、滑点、手续费、Gas 估算、延迟和失败成本；记录报价时间与来源。
不能拿聪明钱成交价当自己的成交价，也不能使用事后信息决定模拟入场。
实盘 M3 必须另行确认预算、风控、签名与权限方案；本交付不授权实现或开启实盘。
